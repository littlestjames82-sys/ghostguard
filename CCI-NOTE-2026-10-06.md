# Cryptographic Context Injection (CCI) — what it means for GhostGuard

Date: 2026-10-06
Source report: Adversa AI via SmartChunks summary — https://smartchunks.com/github-copilot-cli-cryptographic-prompt-injection-vulnerability/
Reported to GitHub: 2026-09-17. GitHub declined to classify it as a product vulnerability.

## The technique, in brief (own summary)

- Malicious instructions are encrypted before an agent sees them. Static
  text filters scan the ciphertext and find nothing suspicious.
- The agent is persuaded to decrypt the text inside its own code-execution
  runtime. The real instruction only exists after that step — inside the
  runtime, past the filter.
- In the most severe reported chain, material from a local `.env` file was
  used and secrets were sent out over HTTP.
- Reported model variance: Microsoft's mai-code-1.1-flash model was
  reportedly fooled about half the time in testing; OpenAI GPT-5.6 models
  reportedly refused every tested payload. Treat these as the researchers'
  reported results, not independently verified here.
- The same team reportedly found a near-identical issue in Grok about two
  months earlier, so this reads as a general agent pattern, not a
  Copilot-only bug.

## Why this is not the same failure mode as GhostGuard's

GhostGuard does not scan instruction text at all. It gates *effects*:

1. Every proposed action is classified (`READ`, `EXECUTE`, `NETWORK_WRITE`,
   `COMMUNICATE`, `SPEND`, `DELETE`, etc.), evaluated by policy, and
   recorded — before it runs. No record, no action.
2. The record carries the *exact payload that will run*, post-resolution
   (`src/gateway.ts`: `action_payload`), and an `ask` verdict surfaces
   exactly that payload to a human.
3. Policy is fail-closed and tier-ordered: no matching rule = deny, and a
   later `allow` can never outrank a `deny`.

So a decrypted "zombie" instruction still has to become an action, and
that action still hits the gateway. Decryption itself is an `EXECUTE`;
exfiltration is a `NETWORK_WRITE` / `COMMUNICATE`. Encryption blinds a
*content filter*; it does not remove the *effect* from the gateway's view.

## The honest caveat

- If a payload is still opaque ciphertext at decision time and only
  becomes meaningful inside execution, a payload-field rule cannot inspect
  the plaintext either. The defence there is class-level, not
  content-level: default-deny / ask on consequential classes, locked rules
  that cannot be weakened by an overlay, and `initiator != actor` so
  unattended runs can be held stricter.
- Under GhostGuard's shipped default policy, `DEPLOY`, `PUBLISH`,
  `COMMUNICATE`, `SPEND`, and `DELETE` ask first. Classes outside that
  list can allow by default — so an integrator who maps an outbound HTTP
  exfiltration to a permissive class weakens the protection. Classification
  discipline ("when in doubt, classify up") is load-bearing.
